# Dependency Version Audit: `.rebase/` → upstream release/1.143

**Date:** 2026-10-31  
**Target upstream:** `release/1.143` (`e646868227c3e3a9e3f24277c8c7220be42c0be7`)  
**Previous upstream:** `release/1.128`  
**Branch:** `alignment-with-upstream-1-143`

## Method

1. **Direct deps (fast pass):** every `dependencies` / `devDependencies` pin in `.rebase/add/` and `.rebase/override/` compared against `git show upstream-code/release/1.143:<path>`.
2. **Transitive `overrides` (npm ls pass):** temporary worktree `/tmp/upstream-vscode-1.143` at `upstream-code/release/1.143`, Node `24.18.0` (1.143 `.nvmrc`), `npm install --ignore-scripts` in each of the 25 directories that had overrides, then one batched `npm ls <pkgs…>` per directory. No upstream lock file changed during install, so the resolved tree is exactly upstream's lock.
3. **Classification rule for transitive overrides** (skill Step 3): **REDUNDANT** if every instance matching the override selector/scope already resolves to a version ≥ the Che pin; **KEEP** if any instance is below the pin; **ORPHANED** if the package or scoped parent is absent from the tree.
4. **Post-audit simulation:** for all 15 directories that still have rules, the post-audit `.rebase/override` + `.rebase/add` files were applied to the upstream 1.143 `package.json` with the same `jq` merge as `override_json_file()` in `rebase.sh`. Then `npm install --ignore-scripts` ran on top of the upstream lock, the same flow as `resolve_package_lock()`. Results:
   - All 15 installs succeeded (no `EOVERRIDE`).
   - Every removed override's package still resolves to ≥ the old pin in the simulated Che tree.
   - Every kept override still has a target in the tree.
   - Packages pulled in only by Che (for example `@kubernetes/client-node` in `remote/`, or the root `postcss@8` override) were checked in this simulated tree instead of the upstream tree.
5. Worktree removed after the audit (`git worktree remove /tmp/upstream-vscode-1.143 --force`).

> **Lock files were not touched.** `package-lock.json` files are regenerated by `rebase.sh` (`resolve_package_lock`), and lock-file stability is verified **after** `rebase.sh` runs (see Recommended Follow-up).

## Legend

| Action | Meaning |
|--------|---------|
| **KEEP** | `.rebase/add/` entry: dependency does not exist in upstream, or some instance in the resolved tree is still below the Che pin |
| **REMOVE** | `.rebase/add/` direct dependency that upstream now declares at an equal or higher version (`add` = "absent in upstream" no longer holds) |
| **REDUNDANT** | Override whose every targeted instance in the upstream 1.143 resolved tree is already ≥ the Che pin (transitive), or whose spec equals upstream (direct). Removed. |
| **ORPHANED** | Transitive override whose package/parent no longer exists in the tree (`npm ls` → empty). None found in this audit. |
| **ACTIVE** | `.rebase/override/` direct-dep entry: Che pin > upstream; still overriding |
| **OUTDATED** | `.rebase/override/` direct-dep entry: Che pin < upstream; upstream is newer. Removed. |
| **MOVE** | Pin kept, but relocated (here: different `package.json` section because upstream moved the dependency) |
| **KEEP (exception)** | Pinned exception: never change regardless of upstream |

`code/` handling for removed entries (skill Step 6.5): if the entry exists in upstream `release/1.128` (current base of `code/`), the `code/` value is restored to the 1.128 value. Otherwise (Che-only), the entry is deleted from `code/`. All removed transitive overrides were Che-only (no upstream 1.128 `overrides` key overlaps), so they were deleted from `code/`.
